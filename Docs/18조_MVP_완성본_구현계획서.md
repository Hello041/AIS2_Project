## 1. 목표

11/18에 **간단한 데모 프로토타입**을 시연한다. 시연 흐름은 다음과 같다.

## 5. 추론 서버 설계

### 5.1 Detector 인터페이스

모델 하나가 모듈 하나다. 모델을 추가·교체·제거해도 `main.py`와 `banding.py`는 고치지 않는다.

```python
class Detector:
    name: str                              # "univfd" | "aide" | "npr"
    def load(self) -> None: ...            # 서버 시작 시 1회 호출
    def score(self, img: PIL.Image) -> float:
        """0~1 원점수. 클수록 AI 생성 쪽. 확률이 아님."""
```

- 모든 모델은 원점수를 **0~1 범위, 클수록 AI 생성 쪽**으로 맞춰서 반환한다(필요하면 sigmoid를 적용). 이렇게 해야 경계값을 같은 방식으로 다룰 수 있다.
- UnivFD는 CLIP의 **이미지 인코더만** 올린다. 텍스트 인코더는 쓰지 않으므로 메모리를 약 0.5GB 아낄 수 있다.
- 모델은 서버를 시작할 때 모두 올려 두고, 요청마다 다시 올리지 않는다.
- 추론은 `torch.inference_mode()`, 배치 크기 1로 한다.

### 5.2 경계값 — `thresholds.yaml`

```yaml
# 임시값. 검증 이미지 점수 분포를 보고 모델별로 조정한다.
univfd: { low: 0.3, high: 0.7 }
aide:   { low: 0.3, high: 0.7 }
npr:    { low: 0.3, high: 0.7 }
```

- `score < low` → `weak`(AI 흔적 약함)
- `low ≤ score ≤ high` → `uncertain`(판단하기 어려움)
- `score > high` → `strong`(AI 흔적 강함)

### 5.3 종합 판정 — `banding.overall()`

종합 판정 로직은 이 함수 하나에만 둔다. `ensemble.yaml`이 있으면 스태킹 방식(단계 1)을 쓰고, 없으면 규칙 방식(단계 0)을 쓴다. 앙상블에 문제가 생기면 이 파일만 지워서 규칙 방식으로 되돌린다.

**단계 0 — 규칙 방식**

1. `strong`과 `weak`가 함께 있으면 → `uncertain` (모델 판단이 정반대)
2. 그렇지 않으면 → 2개 이상 나온 구간
3. 셋이 모두 다르면 → `uncertain`

- 모델이 2개뿐일 때(대체 전 임시 상황)는 두 구간이 같으면 그 구간, 다르면 `uncertain`으로 한다.
- 이 규칙은 실제 사진이 '강함'으로 잘못 판정되는 일을 줄이는 쪽(FPR 우선)으로 기울어 있다.

**단계 1 — 스태킹 방식**

1. 보정: 모델마다 Platt scaling(`p_i = sigmoid(a_i · raw_i + b_i)`)을 적용한다.
2. 융합: 보정된 세 점수 `p_1..p_3`을 입력으로 하는 로지스틱 회귀로 융합 점수 `f`를 계산한다.
3. 불일치: `max(p) − min(p) > τ`이면 `f`와 관계없이 `uncertain`으로 한다.
4. 구간: `f < t_low` → `weak`, `f > t_high` → `strong`, 나머지는 `uncertain`으로 한다.
   - `t_high`는 학습 데이터의 실제 사진 중 `strong`으로 판정되는 비율(FPR)이 5% 이하가 되도록 정한다.

```yaml
# ensemble.yaml — ml/fit_ensemble.py가 생성. 손으로 고치지 않는다.
calibration: { univfd: [a, b], aide: [a, b], npr: [a, b] }
stacking:    { weights: [w1, w2, w3], bias: c }
disagreement_tau: 0.5
bands:       { low: t_low, high: t_high }
trained_on:  "mvp-200 (2026-11-xx)"
```

- 학습 데이터(MVP): 실제 사진 약 50장 + AI 이미지 약 50장(여러 생성기). 각각 원본과 JPEG 재압축(품질 약 70) 두 가지 버전으로 만들어 약 200장을 쓴다.
- 같은 원본에서 나온 이미지가 학습과 평가에 나뉘어 들어가지 않도록 **원본 ID 기준으로 교차검증**(`GroupKFold`, 5-fold)한다.
- **채택 기준**: 교차검증에서 스태킹 방식의 FPR이 규칙 방식보다 높지 않고, '강함/약함'으로 판정한 이미지의 정확도가 규칙 방식 이상이어야 데모에 쓴다. 기준을 넘지 못하면 단계 0으로 시연하고, 비교 결과는 발표 자료에 넣는다.
- 데이터가 200장이므로 이 경계값은 **임시값**이다. 확정은 단계 2(800장)에서 한다.
- 이 데이터셋은 Sprint 2의 800장 데이터셋에 그대로 포함한다. `manifest.csv`의 형식도 그대로 이어 쓴다.

### 5.4 API

**`GET /health`** — 앱이 홈 화면에 들어올 때 호출해 연결을 확인한다.

```json
{ "status": "ok", "models": ["univfd", "aide", "npr"] }
```

**`POST /analyze`** — `multipart/form-data`, 필드 이름은 `image`

성공(200):

```json
{
  "overall": "uncertain",
  "overall_method": "stacking",
  "models": [
    { "name": "univfd", "raw_score": 0.52, "band": "uncertain" },
    { "name": "aide",   "raw_score": 0.81, "band": "strong" },
    { "name": "npr",    "raw_score": 0.12, "band": "weak" }
  ],
  "provenance": null,
  "elapsed_ms": 8421,
  "disclaimer": "본 결과는 참고용이며 AI 생성 여부를 보장하지 않습니다."
}
```

- `band` 값: `weak` | `uncertain` | `strong`
- `overall_method` 값: `rule` | `stacking`. 앱은 이 값을 화면에 표시하지 않으며 디버깅에만 쓴다.
- 모델별 `band`는 어느 방식이든 `thresholds.yaml`의 원점수 경계값으로 정한다. 종합 판정 방식이 바뀌어도 앱 화면은 그대로다.
- **앱은 `raw_score`를 화면에 표시하지 않는다.** 원점수는 디버깅과 이후 보정·앙상블 학습에 쓰기 위해 응답에 넣는다.
- `provenance`: C2PA를 구현하지 않았으면 `null`이다. 구현하면 `{ "c2pa": "none" | "valid" | "invalid", "summary": "...", "exif": {...} }` 형식으로 채운다. GPS 정보는 넣지 않는다.

실패:

| 코드 | 상황 | 앱 표시 |
|---|---|---|
| 400 | 형식이 JPEG/PNG/WebP가 아니거나 디코딩 실패 | "지원하지 않는 이미지입니다" |
| 413 | 10MB 초과 | "10MB 이하 이미지를 선택해 주세요" |
| 500 | 추론 중 오류 | "분석에 실패했습니다" + 재시도 |

- 형식과 크기는 앱에서 먼저 검사하고, 서버에서 한 번 더 검사한다.
- 서버는 받은 이미지를 `BytesIO`로만 다룬다. 파일로 저장하지 않으며, 로그에는 크기와 처리 시간만 남긴다.

## 6. 앱 설계 (Expo)

### 화면

1. **홈**: '이미지 선택' 버튼. 화면에 들어오면 `/health`를 호출해 서버 연결 상태를 표시한다.
2. **분석 중**: 진행 단계 표시(서버 연결 → 이미지 확인 → AI 모델 분석 → 결과 생성). 2분이 지나면 요청을 중단하고 실패 화면을 보여준다.
3. **결과**: [BIN0002.png](../BIN0002.png) 시안을 바탕으로 다음과 같이 구성한다.
   - 상단: 종합 배지(`overall`)와 "분석 결과는 참고 정보이며 확정적인 증거가 아닙니다"
   - 출처 확인: `provenance`가 `null`이면 "준비 중", 값이 있으면 C2PA 상태를 표시한다
   - AI 탐지: **모델별 3칸 막대 3줄**. 해당 구간만 강조하고, 숫자와 점(●)은 표시하지 않는다

     ```
     UnivFD  [ 약함 ][■어려움■][ 강함 ]
     AIDE    [ 약함 ][ 어려움 ][■강함■]
     NPR     [■약함■][ 어려움 ][ 강함 ]
     ※ 모델별 추정 구간이며 확률이 아닙니다.
     ```
   - 시안의 '원시 점수', '판단 근거(히트맵)', '판정 안정성', '내 기록 저장' 영역은 이번 데모에서 뺀다.
   - 하단: 참고용 안내 문구(`disclaimer`)

### 구현 메모

- 이미지 선택에는 `expo-image-picker`를 쓴다. 선택 후 MIME 형식과 파일 크기를 검사한다.
- 서버 주소는 `app.config` 또는 `.env`에 `API_BASE_URL`로 둔다. 노트북 IP나 ngrok URL로 바꿀 수 있어야 한다.
- 타임아웃은 `AbortController`로 120초를 건다.
- 서버가 준비되기 전 1주차에는 **가짜 응답(mock)**으로 결과 화면을 먼저 만든다. 가짜 응답의 형식은 §5.4 예시를 그대로 쓴다.

## 7. 메모리·속도 예상과 점검

| 항목 | 예상 메모리 (fp32) |
|---|---|
| UnivFD (CLIP ViT-L/14 이미지 인코더) | 약 1.2GB |
| AIDE (OpenCLIP ConvNeXt-XXL + ResNet 전문가) | 약 3.5~4GB |
| NPR (경량 CNN) | 100MB 미만 |
| PyTorch 런타임 + 추론 중 메모리 | 약 1GB |
| **합계** | **약 6GB** |

위 표는 추정치다. **1주차 첫 작업으로 `ml/measure.py`를 실행해 실제 값을 측정**하고 결과를 이 문서에 기록한다.

**점검 시점: 11/10 (2주차 말)**

- 기준: 세 모델을 함께 올렸을 때 서버 노트북에서 메모리가 부족하지 않고, 이미지 한 장의 분석이 **60초 안에** 끝나야 한다(2분 타임아웃의 절반을 여유로 둠).
- 기준을 넘거나 연결하지 못한 모델이 있으면 그 자리에서 **대체 모델을 정한다.** Detector 인터페이스 덕분에 `detectors/`에 모듈 하나만 바꾸면 된다.
- **앙상블 진행 여부도 함께 정한다.** 이때까지 모델 3개가 동작하고 데이터 100장(원본 기준)을 70% 이상 모았으면 단계 1로 진행한다. 그렇지 않으면 단계 0만으로 데모를 준비하고, 앙상블은 Sprint 2로 넘긴다.
- 대체 모델을 쓰기로 했다면 데이터셋 채점(`score_samples.py`)을 다시 돌려야 한다. 모델 구성이 바뀌면 보정 계수와 융합 가중치도 다시 학습해야 하기 때문이다.

|---|---|---|---|

- 무료 호스팅은 일정 시간 쓰지 않으면 잠든다(Render는 15분 후, HF Spaces는 장시간 미사용 시). 앱의 홈 화면에 들어오면 두 서버의 `/health`를 미리 호출해 깨운다.

### 12.4 분석 기능 상세 (Sprint 2)

#### 앙상블 단계 2

- 검증 데이터: 실제 사진 100장 + AI 이미지 100장(원본 기준), 각각 원본·JPEG(품질 약 70)·Resize(50%)·Screenshot 모사(축소 후 PNG) 4개 버전으로 약 800장. MVP의 200장을 포함한다.
- 학습·평가: `GroupKFold`(원본 ID 기준, 5-fold)로 보정·스태킹·불일치 τ·경계값을 정한다.
- 비교: 모델별 단일, 단순 평균, 규칙 방식, 스태킹을 같은 데이터로 비교한다. 스태킹이 단일 최고 모델보다 FPR이 낮지 않으면 단일 최고 모델을 쓴다(기획서 기준).
- 결과물: 비교표(Accuracy, Precision, Recall, F1, FPR, '판단하기 어려움' 비율)와 확정된 `ensemble.yaml`. 비교표는 최종 보고서에 넣는다.

#### 판정 안정성

- 서버에서 Pillow로 변형 3가지를 만든다(설정은 검증 데이터와 같게 맞춤).
- 원본과 변형 3개에 대해 같은 종합 판정을 실행하고, **버전별 종합 구간**을 막대로 보여준다. MVP의 결정에 맞춰 숫자는 표시하지 않는다.
- 추론 횟수는 4개 버전 × 모델 3개 = 12회다. 전체 분석이 60초를 넘으면 변형 버전에는 가장 가벼운 모델만 쓰고, 화면에 그 모델명을 표시한다.
- 응답 추가 필드:

  ```json
  "robustness": [
    { "variant": "original",   "band": "uncertain" },
    { "variant": "jpeg",       "band": "uncertain" },
    { "variant": "resize",     "band": "weak" },
    { "variant": "screenshot", "band": "uncertain" }
  ]
  ```

#### 히트맵

- 앙상블 결과 자체의 히트맵은 만들기 어렵다. 그래서 대표 모델 하나의 히트맵을 쓰고, 화면에 모델명을 표시한다.
- Sprint 2 첫 주에 두 방법을 짧게 시험해 보고 하나를 고른다: UnivFD(ViT)에는 Attention Rollout, NPR(CNN)에는 Grad-CAM(`pytorch-grad-cam`).
- 원본 위에 반투명하게 겹친 이미지를 짧은 변 512px 이하 PNG로 만들어 base64로 응답에 넣는다. 서버에는 저장하지 않는다.
- 화면 안내 문구: "모델 반응 영역을 보여주는 참고 정보이며, AI 생성의 증거가 아닙니다."

#### UnivFD 전이학습 (조건부)

- 조건: 앙상블 단계 2와 판정 안정성이 끝난 뒤 시간이 남을 때만 진행한다.
- 방식: CLIP 이미지 인코더는 고정하고 분류층만 재학습한다. GenImage 등 공개 데이터셋 일부에서 특징을 한 번 추출해 두고 선형층만 학습하므로 CPU로도 할 수 있다. 데이터는 검증 데이터 800장과 겹치지 않게 한다.
- 전이학습 후에는 점수 분포가 바뀌므로 `score_samples.py` → `fit_ensemble.py`를 다시 돌린다.
- 원본 가중치와 재학습 가중치의 FPR과 변형 전후 판정 변화를 비교해 최종 보고서에 넣는다.

### 12.5 서비스 기능 상세 (Sprint 3)

#### 익명 기기 식별

- 앱을 처음 실행하면 `device_id`(UUID)와 `device_secret`(난수)을 만들어 `expo-secure-store`에 저장한다.
- API 서버는 `device_secret`의 해시만 저장한다. 기록 조회와 삭제 요청에는 두 값을 함께 보내야 한다.
- 회원가입이나 로그인은 없다. 앱을 지우면 기록에 접근할 수 없게 된다는 점을 설정 화면에 안내한다.

#### 분석 흐름과 HMAC

1. 앱 → API `POST /tokens`: API는 오늘 사용량을 확인하고, 한도 안이면 업로드 토큰을 발급한다.
   토큰 = `{device_id, nonce, exp(발급 후 5분)}` + HMAC 서명
2. 앱 → 추론 서버 `POST /analyze` (이미지 + 토큰): 추론 서버는 토큰의 서명과 만료 시각을 검사한 뒤 분석한다.
3. 추론 서버 → 앱: 결과에 `nonce`를 포함해 HMAC 서명을 붙여 반환하고, 원본 이미지를 폐기한다.
4. 앱 → API `POST /records` (결과 + 서명): API는 서명을 검증하고, 같은 `nonce`가 이미 저장됐으면 거부한 뒤 DB에 저장하고 사용량을 1 올린다.

- **사용량은 결과를 저장할 때(4단계) 센다.** 실패한 분석은 결과가 없으므로 자연히 차감되지 않는다(기획서 조건).
- 토큰은 만료 전까지 재시도에 다시 쓸 수 있다. 저장을 건너뛰어 하루 한도를 피하는 경우는 추론 서버의 IP별 분당 20회 제한으로 막는다.
- IP 제한은 두 서버 모두 `slowapi`로 메모리에서 센다(서버 1대 기준이므로 충분함).

#### DB 스키마

```sql
devices (
  id            uuid primary key,
  secret_hash   text not null,
  created_at    timestamptz not null default now()
);

records (
  id              uuid primary key,
  device_id       uuid not null references devices(id) on delete cascade,
  nonce           text not null unique,
  created_at      timestamptz not null default now(),
  overall         text not null,       -- weak | uncertain | strong
  overall_method  text not null,       -- rule | stacking | single
  models          jsonb not null,      -- [{name, raw_score, band}]
  provenance      jsonb,               -- C2PA 상태, EXIF 요약 (GPS 제외)
  robustness      jsonb,               -- [{variant, band}]
  model_version   text not null        -- ensemble.yaml의 trained_on
);

usage_daily (
  device_id  uuid references devices(id) on delete cascade,
  day        date,
  count      int not null default 0,
  primary key (device_id, day)
);
```

- 이미지, 썸네일, 히트맵, 파일명은 저장하지 않는다.
- 익명 통계(구간별 건수, 평균 처리 시간)는 `records`를 집계해서 만든다. 별도 테이블은 두지 않는다.

#### API 서버 엔드포인트

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/health` | 서버 깨우기·상태 확인 |
| POST | `/devices` | 첫 실행 시 기기 등록 |
| POST | `/tokens` | 업로드 토큰 발급 (하루 30회 초과 시 429) |
| POST | `/records` | 서명된 결과 저장 |
| GET | `/records` | 내 기록 목록 (최신순, 페이지 단위) |
| DELETE | `/records/{id}` | 기록 하나 삭제 |
| DELETE | `/records` | 내 기록 전체 삭제 |

#### 앱 화면 추가

- **내 기록**: 목록(기기에 저장한 썸네일 + 종합 구간 + 분석 시각), 상세(결과 화면 재사용), 항목별·전체 삭제
- **썸네일**: 분석이 성공하면 짧은 변 200px로 줄여 `expo-file-system`의 앱 내부 저장소에 `record_id` 이름으로 저장한다. 기록을 삭제하면 썸네일도 함께 지운다.
- **설정**: 앱 정보, 개인정보 처리 안내(원본 폐기, 저장 항목), 전체 기록 삭제
- **결과 화면 주요 결과 규칙**: C2PA 서명이 유효하면 출처 확인 영역을 맨 위로 올리고, AI 탐지는 보조 영역으로 내린다. 그렇지 않으면 AI 탐지가 맨 위에 온다.

### 12.6 최종 응답 형식 (추론 서버 `/analyze`)

```json
{
  "nonce": "…",
  "overall": "uncertain",
  "overall_method": "stacking",
  "models": [{ "name": "univfd", "raw_score": 0.52, "band": "uncertain" }],
  "provenance": { "c2pa": "none", "summary": null, "exif": { "camera": null, "software": null } },
  "heatmap": { "model": "npr", "png_base64": "…" },
  "robustness": [{ "variant": "original", "band": "uncertain" }],
  "model_version": "v800-2026-11-xx",
  "elapsed_ms": 23456,
  "disclaimer": "본 결과는 참고용이며 AI 생성 여부를 보장하지 않습니다.",
  "signature": "hmac-sha256…"
}
```

- `signature`는 `heatmap`을 뺀 나머지 필드를 정렬된 JSON으로 만들어 서명한다. 히트맵은 DB에 저장하지 않으므로 서명할 필요가 없다.
- 앱은 MVP와 마찬가지로 `raw_score`를 화면에 표시하지 않는다.

### 12.9 우선순위와 범위 줄이기

일정이 밀리면 아래 순서의 **뒤쪽부터** 줄인다.

1. 클라우드 배포 + 앱에서 판정까지의 흐름 (최종 시연의 기본)
2. 내 기록 (저장·조회·삭제) + DB
3. 앙상블 단계 2 (800장 비교표) — 보고서의 핵심 수치
4. C2PA 출처 확인 + 주요 결과 규칙
5. 판정 안정성
6. HMAC 서명 + 사용량 제한
7. 히트맵
8. UnivFD 전이학습

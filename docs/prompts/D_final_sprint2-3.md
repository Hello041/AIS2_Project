# D. 최종본 (Sprint 2~3)

- 사용법: 위에서부터 하나씩 Claude Code에 붙여 넣는다. 각 프롬프트는 새 기능 브랜치에서 시작하고, 완료 기준을 확인한 뒤 PR을 올린다. '병행'은 다른 사람이 동시에 진행한다.
- 전제: 저장소 루트에 `CLAUDE.md`, `docs/`에 세 문서가 있다.
- 일정이 밀리면 계획서 §12.9 우선순위의 뒤쪽부터 줄인다.


D는 MVP 이후 시작한다. 시작 전에 미결 사항(CLAUDE.md 하단)을 팀이 먼저 정한다.

### D1. 800장 데이터와 단계 2 비교표

```
앙상블 단계 2를 진행하자. 근거: 계획서 §12.4.
1. make_variants.py를 전체 버전(jpeg70, resize50, screenshot)으로 실행, 원본 200장 기준 800행 확인.
2. score_samples.py 재실행 → fit_ensemble.py에 Accuracy, Precision, Recall, F1 추가, 버전별 결과도 분리.
3. 스태킹이 단일 최고 모델보다 FPR이 낮지 않으면 단일 모델 방식(method='single')을 쓰도록 banding에 반영.
4. 11/22에 600장 미만이면 그 시점 데이터로 확정하고 장수를 보고서에 명시.
```

### D2. 판정 안정성 → D3 히트맵

```
[판정 안정성] inference/variants.py(B5)로 변형 3개를 메모리에서 만들고 같은 overall을 실행해 robustness 필드 추가.
처리 시간이 60초를 넘으면 변형 버전에는 가장 가벼운 모델만 쓰고 응답에 그 모델명을 표시. 앱은 버전별 구간 막대(숫자 없음).

[히트맵] UnivFD Attention Rollout과 NPR Grad-CAM을 샘플 10장으로 비교하는 스크립트를 먼저 만들고,
내가 하나를 고르면 서버에 구현(짧은 변 512px 이하 PNG, base64, 디스크 저장 없음, 모델명 포함).
```

### D4. HF Spaces 배포

```
추론 서버를 Hugging Face Spaces(Docker, CPU)에 배포하자.
1. shared/ 포함 방식(팀 결정)을 반영해 빌드 구성.
2. 가중치를 Space에 넣는 방법(Space 저장소 LFS vs 시작 시 다운로드)을 비교해 제안.
3. 배포 후 처리 시간 재측정, 60초 기준 확인. 잠든 상태에서 첫 요청 시간도 측정.
```

### D5. API 서버·DB → HMAC·기록·사용량 제한

```
[1단계: API 서버·DB] 계획서 §12.5 스키마로 api/ FastAPI 서버, Neon 연결, /devices, /records CRUD. 
usage_daily.day 시간대는 팀 결정값을 쓴다(미정이면 멈추고 묻기).

[2단계: HMAC] 시작 전 팀이 정한 직렬화 방식을 확인한다(검토 1번).
- 권장 선택지: 추론 서버가 서명한 JSON을 '문자열 그대로' payload로 내려주고, 앱은 그 문자열을 파싱하지 않고 /records에 전달.
- shared/hmac.py로 토큰 발급·검증, 결과 서명·검증. 테스트: 조작된 결과, 만료 토큰, 같은 nonce 재전송 모두 거부.

[3단계: 사용량 제한] /tokens 하루 30회(429), slowapi로 IP 분당 20회.
저장을 건너뛰는 우회의 상한(검토 10번)을 계산해 docs/에 적어 둔다.
```
